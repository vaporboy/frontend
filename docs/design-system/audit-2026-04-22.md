## 3. Token Discipline (Current State)

### 3a. Approved Token Locations

**`lib/src/design/tokens/colors.dart`** exports:

- `SoliplexColors` — 30-field value class (background, foreground, primary,
  onPrimary, secondary, etc.)
- `lightSoliplexColors` — const instance with 30 hex values
- `darkSoliplexColors` — const instance with 30 hex values

**`lib/src/design/tokens/spacing.dart`** exports:

- `SoliplexSpacing` — static const doubles: s1=4, s2=8, s3=12, s4=16, s6=24
- Gap: no s5 (20) or s8 (32) despite both values appearing in widget code

**`lib/src/design/tokens/radii.dart`** exports:

- `SoliplexRadii` — sm=6, md=12, lg=16, xl=24
- `soliplexRadii` — singleton const instance
- Supports `lerp()` for animations

**`lib/src/design/tokens/breakpoints.dart`** exports:

- `SoliplexBreakpoints` — desktop=840, tablet=600, mobile=320

**`lib/src/design/tokens/typography.dart`** exports:

  through labelSmall), all parameterized by colors

- `SymbolicColors` extension on `ColorScheme` — info, warning, danger, success
  getters using Material `Colors.*` constants (crosses Core/Component boundary

## 6. Implicit Conventions

### 6a. Theme Access Pattern

The dominant access pattern is:

```dart
final theme = Theme.of(context);
// then: theme.colorScheme.*, theme.textTheme.*
```

The custom extension is accessed via `SoliplexTheme.of(context)` which wraps
`Theme.of(context).extension<SoliplexTheme>()!`. This is used much less
frequently than raw `Theme.of(context)`.

### 6b. ThemeExtension Naming Convention

Two ThemeExtensions exist, both following the same pattern:

- `SoliplexTheme extends ThemeExtension<SoliplexTheme>` — core design tokens
- `MarkdownThemeExtension extends ThemeExtension<MarkdownThemeExtension>` —
  rich-text rendering

Both implement `copyWith()`, `lerp()`, and provide a static `of(context)`
convenience accessor (SoliplexTheme only — MarkdownThemeExtension is accessed
directly via `Theme.of(context).extension<MarkdownThemeExtension>()`).

### 6c. SectionCard Widget Pattern

`room_info_widgets.dart` defines `SectionCard`: a Card with Padding(all: 16)
containing a Column with title + SizedBox(8) + children. This is the de facto
container for grouped content in the room info screen. It is not shared beyond
the room module.

### 6d. Alpha-Blended Color Convention

Several widgets construct subtle backgrounds by alpha-blending:

- `colors.primary.withAlpha(25)` — chip selection
- `colors.foreground.withAlpha(15)` — badge background
- `colorScheme.onSurface.withAlpha(30)` — inline code background
- `colorScheme.onSurfaceVariant.withValues(alpha: 0.5)` — disabled text

These are de facto tokens — repeated patterns that produce consistent results
but are not named or centralized.

### 6e. De Facto Spacing Scale

The actual spacing values in use form a larger scale than `SoliplexSpacing`
captures:

| Value | Usage Count | Named Token? |
| ----- | ----------- | :----------: |
| 4     | Frequent    | s1           |
| 8     | Frequent    | s2           |
| 12    | Frequent    | s3           |
| 16    | Frequent    | s4           |
| 20    | ~5          | No           |
| 24    | Frequent    | s6           |
| 32    | ~8          | No           |

### 6f. De Facto Border Radius Scale

The actual border radius values in use form a different scale than
`SoliplexRadii`:

| Value | Usage Count | Named Token?                            |
| ----- | ----------- | :-------------------------------------: |
| 4     | 25+         | No                                      |
| 6     | 4           | sm (exists, rarely referenced by name)  |
| 8     | 30+         | No                                      |
| 12    | 6           | md (exists, used in theme.dart)         |
| 16    | ---         | lg (exists, rarely seen in components)  |
| 24    | ---         | xl (exists, rarely seen in components)  |

The most common radii in widget code (4 and 8) have no named token.

### 6g. Platform-Aware Monospace Font

`typography_x.dart` defines `appMonospaceTextStyle()` and a `context.monospace`
extension. It selects SF Mono on Apple platforms and Roboto Mono elsewhere.
This extension is defined but has **zero observed usages** in `lib/` — widgets
that need monospace text construct their own `TextStyle` inline.

### 6h. Text Style Modification Convention

Widgets consistently use `theme.textTheme.*.copyWith(...)` to derive styles.
No widget constructs a `TextStyle` from scratch without referencing the
theme's text theme as a base (except the diagnostics module, which has several
standalone `TextStyle()` constructions).

## 7. Open Questions

1. **Missing spacing tokens.** Values 20 and 32 appear repeatedly but have no
   named token. Should `SoliplexSpacing` be extended with s5=20 and s8=32, or
   should the usages be consolidated to existing values?

2. **Border radius mismatch.** The most common border radii in widget code
   (4 and 8) do not correspond to any named `SoliplexRadii` token. Meanwhile,
   `sm=6` and `lg=16` / `xl=24` are rarely referenced. Should the token scale
   be realigned to match actual usage?

3. **`SymbolicColors` uses Material palette directly.** The info/warning/danger
   /success getters in `color_scheme_extensions.dart` return `Colors.blue`,
   `Colors.green`, etc. — values that are outside the `SoliplexColors` system.
   Should these become fields on `SoliplexColors` for tenant overridability?

4. **Unused `context.monospace` extension.** `typography_x.dart` defines a
   platform-aware monospace helper, but no widget references it. Widgets that
   need monospace text build their own `TextStyle`. Should this be canonized
   and adopted, or removed?

5. **Single-tenant reality.** Only `assets/branding/soliplex/` exists. The
   `pubspec.yaml`, `flutter_launcher_icons`, and `flutter_native_splash`
   configs all hardcode Soliplex assets. What is the expected timeline for a
   second tenant, and should the design system accommodate runtime tenant
   switching or only build-time flavors?

6. **Color manifest format.** Colors are defined as Dart `const` values in
   `colors.dart`. If tenants need to provide their own palettes, should colors
   move to a JSON/YAML manifest loaded at runtime, or stay as compile-time
   constants in per-tenant Dart files?

7. **Dark theme completeness.** `darkSoliplexColors` exists but
   `soliplexDarkTheme()` does not — only `soliplexLightTheme()` is defined.
   Is dark mode a near-term priority, or is the dark palette aspirational?

8. **No motion tokens.** The spacing, color, and radii token files exist, but
   there are no duration or curve tokens for animations. Is consistent motion
   a design goal?

9. **Diagnostics module styling.** The diagnostics module has the highest
   density of inline `TextStyle` and `EdgeInsets` constructions. Is this
   module considered part of the design system surface, or is it an internal
   developer tool exempt from token discipline?

10. **`SectionCard` scope.** The `SectionCard` widget in `room_info_widgets.dart`
    is the most reusable container pattern but is scoped to the room module.
    Should it be promoted to `lib/src/shared/` or the design system layer?
